## 1. Задача приложения и история решения

Изначальная идея — сделать в HTML5 приложение захвата движения человека **в режиме живой камеры или из заранее снятого видео**, визуально показывать, как двигается 3D-манекен, записывать по времени положения костей и экспортировать **GLB/JSON**. Затем перенести в Android APK. Важный ориентир: созданные движения использовать дальше в Animation Studio и при анимации персонажей для MMORPG.

Первая HTML5-проверка, открытая из Android «Загрузок», работала в `content://...` и сообщала `Permission denied`: веб-страница не имела правильного защищённого контекста камеры. Мы решили не чинить эту проблему только в дизайне HTML, а упаковать сайт в **отдельный Android Capacitor APK**, зарегистрировать Android CAMERA permission и локальную MediaPipe-модель. Для этого пользователь создал отдельный **репозиторий `Mo`**.

После первой APK потребовалось **отказаться от дублирования обеих рук и охватить всё тело**, а не только верх. В видеозаписи предыдущей беседы зафиксировано: «одна рука → одна рука», «две → две», левая/правая нога независимо, голова отдельно, у невидимой конечности нельзя копировать другую. Затем пользователь утвердил две **неоновые иллюстрации суриката**: квадратную — для иконки, вертикальную — для загрузочного экрана. Позже появились импорт собственного привязанного GLB и снижение задержки камеры.

## 2. Технология и архитектура

| Блок | Реальное расположение и принцип |
|---|---|
| UI | `index.html`, `src/style.css` — русский интерфейс, адаптация ширины под смартфоны, источник видео слева и 3D-персонаж справа на широком экране |
| Управление, 3D, запись, экспорт | `src/main.js` — камера, демо, импорт видео, Three.js-сцена и настоящий SkinnedMesh, анимационные кватернионы, GLB/JSON |
| Определение движения | `src/tracking.js` — MediaPipe **33 landmarks**, векторы костей по отдельным индексам левой и правой стороны |
| Пользовательский персонаж | `src/character.js` — нормализация имён, соответствие костей Mixamo/аналогам и приближённая коррекция базиса вращений |
| Android | `capacitor.config.json`, `branding/android/native/`, `scripts/camera-manifest.py` — Capacitor 7, `CAMERA`, Java permission plugin |
| Медиа и рендер | `@mediapipe/tasks-vision 0.10.35`, `three 0.170.x`, `GLTFLoader`, `GLTFExporter`, WebGL |
| Файлы | `@capacitor/filesystem` и `@capacitor/share`; веб-скачивание через Blob |
| Офлайн | `scripts/get-model.sh` скачивает **pose_landmarker_lite.task в CI**, `scripts/copy-wasm.mjs` копирует локальные WASM-модули в сборку |
| APK | `.github/workflows/mocap-android.yml`; Node 22, Java 21, `npm test`, `npm run build`, Capacitor/Gradle `assembleDebug` |

Модели и видео **не отправляются в наш собственный сервер**; распознавание выполняется локально. **Интернет нужен для установки/сборки зависимостей и загрузки модели на этапе подготовки**, а не для обычного распознавания в уже укомплектованной APK.

При открытии в браузере **камера требует HTTPS либо `localhost`**. Скачивание `index.html` и открытие через `content://` — **неподходящий способ проверки камеры**. Для планшета использовать APK.

## 5. Отдельный анализ камеры и задержки

**Уже присутствует:**
- Android `CAMERA` и нативный `MoCapCamera` с запросом runtime-разрешения.
- Capacitor Android использует защищённый `https://localhost`, а не `content://`.
- Запрос фронтальной камеры `facingMode:'user'`, **480×360**, до **30 FPS**.
- `MediaPipe PoseLandmarker` со схемой `VIDEO`, GPU-first и CPU fallback.
- Отрисовка 3D ограничивается приблизительно **30 FPS**, разрешение WebGL-пикселей сокращено для экономии ресурсов.
- Цель детектирования около **24 FPS**, адаптивный интервал от ~32 до 100 мс по длительности инференса; текущее значение операции отображается на экране.
- Сглаживание по умолчанию **12%** вместо более медленных прежних 45%.

**Не доказано и где возможны ошибки:**
- `detectForVideo()` выполняется **синхронно в UI-потоке** браузера. На слабом Android может задерживать рендер/нажатия. GPU-first не гарантирует быстрого GPU на каждой модели планшета.
- Временная задержка от **экспозиции/доставки кадра камеры** до движения 3D-модели **не измеряется**; цифра «Распознавание N мс» — только время работы детектора, не общая задержка.
- Переключение GPU→CPU предусмотрено **при создании распознавателя**, но при последующих runtime-ошибках автоматическое переключение в `infer()` не реализовано: там только предупреждение.
- Схема направления X вычисляет знак по плечам **один раз после старта источника**. При сильном повороте человека или нетипичной ориентации камеры возможны неточности. CSS-зеркало при этом корректно отделено от скелета.
- Для полного тела необходимо **видеть всего человека в кадре**; с планшета вблизи голени/стопы часто вне кадра — это ограничение ракурса и модели, а не доказательство, что ноги вообще не подключены.

## 6. Точность рук, ног и позвоночника

**Что исправили на уровне кода:**
- Каждая сторона получает **свои собственные landmarks**; видимость проверяется для каждого сустава, правая сторона **не берёт координаты левой**.
- Конечность при пропадании точек **удерживает последнюю позу**.
- Голова считается отдельно по ушам/носу; ноги и стопы — по своим индексам.

**Почему результат всё равно может быть неидеальным:**
1. `orientBone()` поворачивает кость так, чтобы её ось приблизилась к направлению сегмента. Это **приближённое решение без полноценной кинематики, учёта ограничений локтей/коленей и полноценной ориентации кистей**. Без теста реальных рук нельзя обещать правильный изгиб каждого сустава.
2. `Spine1` и `Spine2` получают **один и тот же вектор между тазом и плечами** — независимые изгибы разных отделов позвоночника пока не реконструируются.
3. `Hips` вычисляется **условным направлением по оси таза**, а не полным пространственным трекингом таза.
4. Голова оценивается по нескольким лицевым точкам **эвристически**; когда они исчезают, поворот удерживается. Поворачивание головы в профиль может быть менее точным.
5. Для кисти в качестве направления используется запястье→точка на ладони. **Пальцы в деталях не распознаются и не записываются**.
6. **Перемещение всего персонажа** (root translation) не отслеживается/не экспортируется, поэтому ходьба и бег в основном отображаются как **движения конечностей на месте**, а не путешествие по сцене.
7. После продолжительного перекрытия одной конечности её удерживаемая поза может выглядеть «застывшей». Нет отдельного **режима плавного возврата к нейтральной позе** или UI-переключателя способа обработки потери.

**Главное заключение:** требование «одна рука — одна рука, обе руки — обе руки» **заложено в коде и покрыто синтетическими тестами**, но **не закрыто полноценной ручной валидацией**. Не объявлять эту проблему гарантированно решённой только по зелёной сборке.

## 7. Запись, проигрывание и экспорт

В `src/main.js` происходит:
1. После запуска камеры, видео или демо кнопка «Начать запись» очищает старую последовательность.
2. Для каждого обработанного кадра сохраняются `t` (время) и локальные `quaternion` **19 костей** — таз, основные отделы туловища, шея, голова, плечи, локти, кисти, бедра, голени, стопы.
3. «Завершить» переводит в режим просмотра, шкала умеет искать и интерполировать между записями.
4. JSON экспортирует исходные кватернионы тестового скелета и временные метки.
5. GLB экспортирует **реальный SkinnedMesh манекена** с клипом либо **подгруженную ригованную модель**, применяя к клипу сопоставление костей.

**Риски/недоработки:**
- Ограничение **2700 записанных кадров** показывает сообщение «3 минуты». На деле **2700 / 24 ≈ 112,5 секунды**, при 30 кадрах/с — **90 секунд**; длительность зависит от реальной скорости захвата. Это **проверяемая ошибка подписи/логики лимита**, не гарантия трёхминутной записи.
- Записи происходят в **памяти текущей страницы**. **Нет проекта с автосохранением**, выбора ранее записанных движений, монтажа или отдельного редактора ключей.
- **Нет подтверждённого интеграционного теста** «30-секундный захват с камеры → GLB → повторный импорт в Animation Studio/Godot». Текущие тесты для GLB в `tests/ui-v04.test.mjs` проверяют связи элементов и наличие кода, а не реальный экспорт/повторную загрузку сложной модели.
- JSON и GLB на Android временно создаются в **Cache**, затем открывается **системное меню «Поделиться / Сохранить»**. Это **не автоматическое постоянное сохранение в пользовательской папке**. Нужно выбрать приложение/файловый менеджер, которое сохранит документ, иначе после очистки кеша файл исчезнет.
- Для импортированного GLB требуются настоящий `SkinnedMesh`, совместимые имена суставов (примерно Mixamo) и хотя бы частичная гуманоидная структура. **Нестандартные звери, драконы, модели без привязки — не гарантированы**.
- Применяемая `buildRetargetMap/retargetPose` — **базовая коррекция направления rest-позы**, но не пропорциональный скелетный решатель. В зависимости от GLB ноги/плечи могут вращаться неестественно.
- Повторный GLB-экспорт может содержать **различные доступные клипы**, но спецификация одного текущего записанного движения не равна мультитрековому редактору анимаций.

## 10. Приоритеты следующего этапа

### P0 — получить достоверно рабочую APK

1. **Установить последнюю успешную APK №6** из GitHub Actions. Сначала не менять код.
2. Проверить **разрешение камеры** при первой установке, после запрета/повторного разрешения и после перезапуска; убедиться, что модель MediaPipe загружается без интернета.
3. Снять **асимметричные движения** при полном росте: правая рука (левая неподвижна), левая рука (правая неподвижна), одно колено, две руки, кивок и наклон головы. Провести сравнение при переключении «Отразить камеру».
4. Замерить на экране время инференса; снять видео с камеры и манекена одновременно, оценить видимую задержку на устройстве, особенно в движениях плеч.
5. Записать **10–30 секунд**, посмотреть запись назад, экспортировать **JSON и GLB**; обязательно **повторно загрузить GLB** в Animation Studio/Godot/совместимом просмотрщике.
6. Открыть **простой Mixamo-совместимый GLB со SkinnedMesh**, проверить совпавшие суставы, запись и повторный экспорт. Для сложного GLB пока не обещать результат.
7. Если выявлена ошибка, сохранить **короткое видео, модель GLB, экспортный файл, текст ошибки и номер сборки**. Исправлять конкретный баг и проверять регрессии, не переписывая одновременно всю кинематику.

### P1 — уже после P0

- Настоящий **нативный Android splash** с выбранным вертикальным постером.
- Надёжное сохранение GLB/JSON через **Storage Access Framework** без необходимости выбирать «Поделиться», с возможностью указать постоянную папку.
- Улучшенная **калибровка ориентации, стабильности головы и суставов**, а при потере landmarks — настраиваемое «удержать / вернуться плавно».

## 12. Резюме

**MoCap Studio на этапе v0.4 — реальный Android-прототип, а не только макет:** три источника движения, офлайн MediaPipe, 3D-манекен, отдельные конечности, базовый полный скелет, запись и экспорт, импорт совместимого собственного GLB, фирменная графика. **CI подтвердил успешную сборку.**

**Основной незакрытый вопрос — качество поведения на устройстве.** Требования «одна рука → одна», «одна нога → одна», точность суставов, приемлемая задержка, сохранность GLB и удобное сохранение файлов нуждаются в реальной проверке. В коде есть как технические ограничения (нет root motion, 19 экспортируемых костей), так и конкретные UX-недоделки (ненативная заставка, Share вместо устойчивого Save As, лимит 2700 кадров с неточной подписью «3 минуты»).

**Рекомендуемая следующая задача: не новый функционал, а полный цикл «камера → одна рука/нога → запись → экспорт → повторная загрузка на Android» на текущей APK, затем точечная правка выявленных ошибок.**
